# 2026-10-12 실험 기록: 안내점(GP)이 튀는 원인, 정지 반복의 원인, 터미널 10칸 실행 도구

앞선 기록(`2026-10-07_experiments_KR.md`)의 후속이다. 코드와 문서는 `capstone_navi` 브랜치 `jackal-real-drive-fixes-20260912`의
`39fba0b`, `0eef9c3`, `5b6d2ee` 에 있다(이전 날 `58b2fa4`, `d21ac41` 이후). 오프라인 테스트 211개 통과.
오늘 상태는 이미지 `drive-1012`(22.6GB)로 보존했다(컨테이너가 `--rm`이라 이 이미지가 유일한 보존본이다).
이 문서에서 "run / stop"은 주행 시작 / 정지를 뜻한다(용어를 통일했다).

## 1. 요약

- **정지 반복은 두 가지 설정 문제였다.** (a) 트래커의 경로 만료가 1.2초인데 브릿지는 경로를 약 1.0초마다 내서 여유가 0.2초뿐이었다.
  150초 동안 1.2초를 넘는 간격이 성공 주행은 6번(정지 1.4초), 문제 주행은 61번(정지 61.5초). 2.5초로 늘려 해결했다.
  (b) LIO(FAST-LIVO)가 2시간 돌면서 CPU 365%, 메모리 980MB, 호스트 load 19까지 커져 센서가 끊겼다. LIO를 재시작하면 CPU 50%로 돌아왔다.
- **GP(안내점)가 장애물에 붙고 앞뒤로 튀는 원인을 기록으로 확인했다.** 다만 **개선은 부분적**이다(아래 4절).
- 안전 보조 경로(FB)의 사용 비율은 좋은 주행에서 매우 낮았다(경로 갱신의 1.6%: 125번 중 2번, 2.4%: 166번 중 4번). 나쁜 주행에서는 29%(62번 중 18번)~41%였다.
- 장애물이 있는 구간을 **정지 0.0~0.4초, 10m당 회전 166~176°**로 지나간 주행이 두 번 있었다(하나는 사용자 직접 주행).
  다만 장애물 배치가 매번 달랐고 어려운 배치(복도 중앙 근처)에서는 결과가 나빴다.
- 아직 해결 못한 것: GP 점프(1m 이상 이동 비율 약 21%), 어려운 배치에서의 좌우 번복, 사용자 주행 한 번이 목표 3.4m 앞에서 끝난 원인 미확인, 보행자.

## 3. "장애물 쪽으로 간다"의 원인 (`bag_115330`)

- 복도 오른쪽 벽 y=-0.5m, 왼쪽 벽 y=+1.75m, 박스 정면 x≈3.3m(y -0.25~+0.5m). **지나갈 길은 왼쪽 1.25m 틈뿐**이었다.
- 모델/보조 후보는 앞 약 1m만 보고 검증한다. 박스가 1.4m 앞에 올 때까지 오른쪽도 안전해 보였고 후보 순위가 4/5 → 1/5 → 4/5 → 3/5로 흔들렸다.
- 이전에 넣은 연속 조향은 방향은 맞았으나 힘이 약해(0.2rad/s) 경로 추종에 졌다.
- 대응: 틈 따라가기(직진선에 장애물이 있으면 양쪽이 막힌 0.85m 이상의 틈을 찾아 그쪽으로 향함, 벽 뒤의 안 보이는 공간은 틈이 아님),
  방향 상한 0.5rad(`bag_105520`에서 1.12rad까지 요구해 속도가 줄고 제자리 회전처럼 됨), 측 유지 가중치 2.0.
  같은 스캔 재생에서 방향 최대값은 1.12 → 0.50, 0.5rad 초과는 71 → 0번이었다. **좌우 번복(13번)은 그대로**였다.

## 4. GP가 튀는 원인과 결과

원인(코드와 `bag_110814`, `bag_112959`로 확인):
1. GP는 "로봇 앞 경로 위에서 직선이 0.44m 이상 안전한 가장 먼 점"이다. 박스가 가까워지면 먼 점으로 가는 직선이 막혀 GP가 로봇 쪽으로 줄고(1.3 → 0.5m), 박스를 지나면 앞으로 튄다.
2. Nav2 글로벌 경로가 주행 중 박스를 보고 다시 계획된다(예: x=-1.5에서 경로 y가 -0.34 → +0.25). GP가 새 경로를 따라 좌우로 건너뛴다.
3. `guidance_radius`가 8.0m라서 앞이 트이면 GP가 7~8m 앞, 막히면 0.4m(최대 7.6m 점프).
4. 박스 0.3~0.44m 안으로 들어간 상태, 또는 경로 주변이 모두 막히면 GP를 못 찾아 `adaptive_guidance_failed` 정지(`bag_112032`에서 14번, 정지 5번).

대응과 효과:

| 지표 | 개선 전(`bag_110814`/`bag_112959`) | 개선 후(`bag_120619`) |
|---|---|---|
| 로봇~GP 최대 거리 | 7.9m | 3.9m (4m 상한) |
| GP~장애물 여유 중앙값 / 0.55m 미만 비율 | 0.59~0.62m / 32% | 0.73m / 15% |
| GP가 1m 넘게 움직인 비율 / 최대 | 20/60 (28%) / 7.6m | 15/72 (21%) / 3.9m |

적용: 0.65m 여유 선호(앞 1.5m 이상), 최대 앞 거리 4m, 한 번에 0.8m / 뒤로 0.3m 제한(막히면 사이에서 안전한 점), 경로 옆 0.4~1.3m 점 탐색, 탈출 반경 재탐색, 목표 도달 반경 0.5 → 0.7m.
**모두 단위 테스트와 위 기록 비교로만 확인했고, 점프 비율 21%는 아직 높다.**

## 4-1. 화면(RViz) 표시 결정

녹화·발표를 위해 화면을 정리했다: 글로벌 경로 숨김, 실행 경로 하나(굵은 초록), 지나온 궤적(파랑), 안내점 1.0m 안의 안전한 후보만, 충돌 검사 표시와 거절 후보 숨김
(**로그와 rosbag에는 그대로 남음**), 축·TF 표시 제거. 안전 보조 경로가 실행 중일 때만 작은 `FB` 글씨를 띄운다.
**`FB` 표시를 없애거나 모델 경로로 보이게 하는 요청은 하지 않았다.** 경로를 누가 만들었는지 보여 주는 유일한 표시라서 화면에 남긴다.
발표에는 "FB = 안전 보조 경로" 범례를 넣는 방식을 권했고, 모델 단독 주행 모드는 아직 만들지 않았다.

## 5. 도구와 운영

- `field_scripts/open_jackal_terminals.bash`: terminator 한 창을 10칸으로 분할(왼쪽 준비 5칸, 오른쪽 주행 5칸). 각 칸에 명령이 입력만 되어 있고 Enter로 실행. 6번 STATUS만 자동.
  `--no-dbus`가 필요하다(이미 떠 있는 terminator가 새 창을 가로채 배치 파일이 무시됨). GNOME(Wayland)이 창 위치를 가끔 무시해 터미널 폭을 46%로 줄여 RViz(오른쪽)와 겹치지 않게 했다.
- `check_ready.bash`, `stop_all.bash`, `restart_lio.bash`, `odom_trail.py`(주행 시작에 지워지는 궤적), `place_window.py`(창 이동 시도, 불안정), 녹화용 RViz 배치.
- `monitor_run.bash`: 이제 **Ctrl+C / 창 닫기 / kill에도 정지**한다(대역 스크립트로만 검증). rosbag이 없으면 시작하고, 살아 있지 않으면 시작하지 않는다.
- 용어 통일: 주행 시작과 정지를 모두 run / stop 으로 부른다(트래커 상태 문자열, 서비스 응답, 스크립트, 문서). 컨테이너 `moai_jackal_spubert`, 이미지 `drive-NNNN`, 로그 링크 `drive_latest`.
- 절차 문서: `real_jackal/DRIVE_PROCEDURE_KR.md`.

## 6. 사고와 교훈

- **내가 실행한 `stop_all`이 사용자가 켜 둔 스택을 껐다.** 문서용 스크립트를 시험 삼아 돌렸는데 그 사이 사용자가 12:03에 새로 켜 둔 상태였다. 로봇은 이미 정지(트래커 stopped)였으나 센서, Nav2, 브릿지, RViz가 꺼졌다. 스크립트와 문서에 "실행 중인 스택을 모두 끈다" 경고를 넣었다. **실행 중일 수 있는 시스템에 파괴적인 시험 명령을 돌리기 전에 상태를 먼저 확인한다.**
- rosbag이 `SQLite database is locked`로 죽었다(기록 중인 DB를 읽은 것으로 추정). 기록 중에는 DB를 열지 않는다.
- `pkill -f`/`pgrep -f` 패턴이 내 명령줄에도 있어서 내 셸이 종료되는 사고가 여러 번 있었다. 대괄호 패턴 또는 pid로 종료한다.
- 명령을 설명할 때 긴 경로를 `…`로 줄여 쓴 것을 사용자가 그대로 복사해서 `Calibration directory must contain …` 에러가 났다. 명령은 줄이지 않고 전체로 쓴다.
- 이미 켜져 있는 센서/Nav2를 다시 켜면 노드가 중복된다. 터미널 1~3번 칸은 처음 한 번만.
- 안전 검사가 "삭제처럼 보이는" 줄 삭제 명령(`sed -i '/…/d'`)을 막았다. 목록 파일은 수정하지 않고 마지막 항목만 읽는다.
